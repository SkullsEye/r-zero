R-Zero: fraud as a contagion

Card fraud is not a set of independent bad transactions. It is a branching process with a half-life of minutes. Measuring that half-life produces a feature family that doubles a strong detector — and a way to prove the gain is real.

Umar Bin Muzzafar Dayananda Sagar University IEEE-CIS · 590,540 transactions · 182 days

01 What this is

A detector, a decision layer, and a price on every outcome

Three questions, answered in order. Is this transaction risky? Have we seen enough to act? And what is that action worth in rupees?

Most fraud systems answer only the first, hand a score to a threshold, and call the threshold a policy. This system answers all three, and every number below is measured on 62 days of transactions the model never saw during training or tuning.

A metric this document deliberately does not report

Accuracy. At a 3.4% fraud rate, a model that answers "not fraud" to every transaction scores 96.6% accuracy and catches nothing. Accuracy is uninformative on imbalanced data and its absence here is a choice, not an omission. Precision at a fixed review depth, recall, PR-AUC and rupees are the metrics that survive contact with an operations team.

02 The finding

Fraud reproduces, and the rate is measurable

A fraudster who finds a working card does not stop; they run more within the hour. A technique that works gets repeated. Fraud arrives in outbreaks, not as scattered independent events — yet almost every production system scores each transaction as though the previous two hundred told it nothing.

Seismologists faced the same structure with earthquake aftershocks and solved it in the 1970s. The intensity of events at time t is a background rate plus a decaying contribution from everything that already happened:

λ(t) = μ · s(t) + Σti < t α · e−β(t − ti)
μ is the background rate, s(t) the ordinary daily rhythm of traffic, α how much each event lifts the near-future rate, and β how quickly that lift fades. The ratio R₀ = α / β is the mean number of further events each event causes — the same reproduction number epidemiologists use, because a self-exciting point process and a branching process are the same mathematical object.

Fitted on real labelled fraud, twice, on unrelated datasets:

Both are decisively below 1, so outbreaks die out rather than exploding — and both are decisively above zero. A null model with no self-excitation, matched on event count and daily rhythm, produced a maximum R₀ of 0.043 across 50 simulations against an observed 0.438.

The consequence that matters

The half-life is minutes. That single fact rules out an entire class of architecture: a system that scores transactions in a nightly batch has already missed every outbreak it was built to catch. It also means proximity to fraud cannot be a fixed property of a graph — it has to be measured at a moment.

03 The invention

Contagion features: the graph, multiplied by the clock

Production fraud systems carry two kinds of derived signal. Graph features are static — who is this account connected to, how large is its component, what is its PageRank. Velocity features are purely temporal — how many transactions in the last hour, how much spent today. Both are standard. Neither is multiplied by the other.

Section 02 is the reason they must be. A device that touched confirmed fraud four minutes ago and the same device four weeks later are entirely different risks, and no static graph feature can separate them.

Formally, this is a Hawkes process running on the entity graph rather than on a single event stream:

contagione(t) = Σj ∈ frauds on e, confirmed before t w(e) · e−β(t − tj)

w(e) = 1 / log( degree(e) + 5 )
Computed for nine entity families — card, full card signature, billing address, client key, device, device-and-browser, sending email domain, receiving email domain, screen resolution — at three decay rates with half-lives of roughly one hour, one day and one week. Twenty-seven features in total. The weight w(e) is Fraudar's camouflage discount: an attribute shared by hundreds of thousands of people carries almost no identity, so it contributes almost nothing per event.

Why three decay rates rather than one

A card-testing burst and a slow mule ring do not live on the same clock. One resolves in minutes; the other accumulates over a fortnight. A single window forces a choice between them; running three in parallel lets the model decide which timescale matters for each entity family. In the fitted model, the one-hour and seven-day variants of the same entity are used differently and independently.

The property that makes it shippable

Because the kernel is exponential, the running total needs no history buffer and no window. Between two events on the same entity it is one multiply; at an event it is one add:

accumulated *= exp(-decay_rate * elapsed)
accumulated += weight

That is O(1) per event — the same trick behind an exponential moving average. The feature is therefore computable on a live stream, which given a half-life of minutes is not an optimisation but a requirement.

04 Architecture

Five stages, and a feedback loop that closes

Stage 2 — features

124 features in three families, all built in a single forward pass over time so a transaction can only ever observe its own past. The velocity family is standard practice computed carefully; the contagion family is described in section 03.

Stage 3 — detector

Gradient-boosted trees, early-stopped on a held-out window that is always later than the training window and always earlier than the scoring window. Deliberately unexotic: the claim of this project rests on the features, so the model is the one a competent team would reach for first, and the comparison in section 06 is against the same model without contagion.

Stage 4 — sequential test

Rather than judging each transaction alone, evidence accumulates across a client's transactions and a verdict is issued the moment it becomes conclusive — Wald's sequential probability ratio test, whose stopping rule is provably the fastest for a given pair of error rates. Section 08 records how that guarantee failed here and what replaced it.

Stage 5 — policy

Scores become actions under two hard constraints: a finite review queue, and a ceiling on how much of the day's volume may be blocked automatically. Both bind on the final action, and neither can be encoded away — an illegal policy is unrepresentable in the search space rather than merely penalised.

Every outcome has a price

A missed fraud costs the transaction value plus the chargeback fee. A review costs an analyst's time. Wrongly blocking a real customer costs a support contact plus the probability that they never return — the term most cost models omit and the one that dominates at scale. Because there is no single best trade-off between catching fraud and stopping good customers, the system returns a frontier of 60 defensible settings and the merchant chooses.

05 Data & protocol

A split designed so the numbers cannot flatter themselves

IEEE-CIS (Vesta): 590,540 real card transactions over 182 continuous days, 20,663 confirmed frauds, one-second timestamps, and the entity columns — card, address, email domain, device, browser, screen — the contagion features are built on.

Label lag

In production nobody learns a transaction was fraudulent the instant it settles; a chargeback arrives days or weeks later. A fraud therefore enters the contagion state only seven days after it occurred. Setting that delay to zero improves every number in this document and would be a lie.

Causality

Where two events share a timestamp, reads are served before writes, so a transaction can never observe an outcome recorded at the same instant as itself — including its own. This is a one-line ordering decision with no visible effect on any headline number, and it is the difference between a causal feature and a leaked one.

07 Breaking it

A doubling is when you should suspect yourself

The most common cause of a large jump in a fraud model is not a good idea; it is a feature that has seen the future. Three attacks, run against our own headline.

Attack 1 — shuffled labels

Rebuild the identical contagion features from randomly permuted labels and retrain everything else unchanged. Structure that leaks would survive this; a real signal cannot.

Contagion features built fromPR-AUC
nothing — family removed entirely0.2016
randomly shuffled labels0.1964
real confirmed fraud0.4013

Noise-built features land at 0.1964 — statistically indistinguishable from having no contagion features at all. The entire gain comes from real fraud structure.

Attack 2 — how fast must the feedback arrive?

If the lift needs same-day labels it is a laboratory result. Varying the confirmation delay: 0d → 0.652, 7d → 0.401, 21d → 0.387, 45d → 0.259, 90d → 0.202. It degrades gracefully and is still substantial at three weeks. Every number in this document uses the seven-day figure.

Attack 3 — cut the feedback loop entirely

Deploy the system and never tell it about another fraud again. PR-AUC falls from 0.401 to 0.303, against 0.202 with no contagion at all — 51% of the benefit survives with the feedback loop dead. That belongs in the model card: this system needs a confirmed-fraud feed, and fails gracefully rather than off a cliff without one.

And 39 tests that try to make the features lie

Among them: flipping a single transaction's outcome must not change that transaction's own features by a single bit, at zero label lag — the hardest case. Simultaneous events must be read before they are written. A longer confirmation delay must weaken the feature monotonically. An attribute shared by everyone must contribute less per event than a rare one. All 39 pass, and they run in under twenty seconds.

08 What failed

Four claims that did not survive their own tests

Each of these was believed, tested, and found wanting. They are recorded here because a system whose every claim happened to hold is a system that was not tested hard enough.

1

Careful machinery on an unmeasured signal

The first working version had a sequential decision layer, a cost model and an evolved policy frontier — sitting on a graph-propagation score of PR-AUC 0.14, when a standard gradient booster reaches 0.23. Everything had been measured except whether the thing at the centre was any good.

Fixed: benchmark the detector against the obvious baseline first. The same downstream machinery then went from ₹34.0M to ₹58.5M.

2

Wald's guarantee does not hold on client data

The sequential test was designed for a 1% false-alarm rate and delivered 10.6%. Wald's theorem assumes each observation is independent evidence; a single client's transactions are near-identical, so the same fact was counted repeatedly and the statistic raced to the boundary.

Fixed: keep the sequential structure, but set the boundary empirically on held-out data instead of from the closed form. Now 2.14% against a 1% target — better, still imperfect, and described in the model card as an empirical bound that needs periodic recalibration rather than a theoretical guarantee.

3

The genetic algorithm does not find better policies

Evolution was justified on the grounds that the policy space is non-differentiable and multi-modal. Given an identical evaluation budget, random search matches it — at four parameters and at ten.

Fixed: the claim was narrowed to what the measurement supports. NSGA-II returns 60 evenly spaced operating points where random search returns six clumped ones. It is a better menu, not a better optimum, and the test suite keeps the honest converse as a passing assertion.

4

Velocity features made the model worse

Adding 72 causal history features dropped PR-AUC from 0.230 to 0.202. Removing the features with the worst train-to-test drift did not recover it.

Diagnosed: this dataset's own C and D columns are already professionally engineered velocity features, so ours are redundant and contribute only overfitting surface. This strengthens rather than weakens the central claim — contagion adds its lift on top of a model that already has expert velocity features.

09 Limits

What would have to be true before this ran on live money

  • It is not state of the art as a detector. Heavily tuned ensembles on this dataset score higher. The claim is a novel and independent source of lift that stacks on whatever detector already exists — not that this model beats them.
  • The false-alarm bound is empirical and drifts. 2.14% against a 1% target, calibrated on one window and applied to the next. Production would need rolling recalibration and an alarm when the achieved rate leaves its band.
  • It requires a confirmed-fraud feed. Roughly half the contagion benefit depends on outcomes flowing back within days. A merchant with slow chargeback reporting gets the degraded version measured in section 07.
  • Cost parameters are assumptions. Churn probability after a wrongful block is the most consequential and the least observable number in the model. It should be estimated from the merchant's own data, not guessed.
  • Segment fairness is unmeasured. Contagion propagates through shared attributes, and shared attributes correlate with geography and device affordability. A disparate-impact audit across regions and price tiers is required before deployment and has not been done.
  • One dataset, one geography. R₀ replicates across two independent datasets; the contagion lift has been measured on one. It should be re-measured on Indian traffic before any number here is quoted to a merchant.
