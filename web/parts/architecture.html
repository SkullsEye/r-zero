Architecture

One object, two methods, and a hard rule about time

The whole system is a small amount of state that answers questions about the present using only what has already been confirmed. Everything else — the model, the policy, the money — is ordinary machinery sitting on top of that one guarantee.

The request path

A transaction arrives and leaves with a decision. Contagion state is read before it is written, which is the invariant everything else rests on: a transaction can never contribute to its own features.

Read before write, at a tied timestamp

Two transactions can share a second. If a contribution lands before a read at the same instant, a transaction sees a fraud it could not have known about, and the whole result is quietly invalid. So every event is sorted by time first and by kind second, with reads ordered ahead of writes.

The temporal protocol

Two models are trained rather than one, so no period is ever scored by a model that used it in any capacity, including for early stopping. The policy is evolved on scores the final model produced for a period it did not train on, then applied untouched.

The state, exactly

Per identity, per decay rate, the system keeps two numbers: an accumulator and the clock it was last touched. That is the whole of it. Everything else is derived.

identity: accumulated[3] # one per half-life updated_at[3] # when it last moved count, total # plain history first_seen, last_seen

11,355 identities fit in 1.4 MB. A snapshot is a plain dictionary, so a restart restores in one read and the object is trivially shardable by identity.

Four ways in

In order of how little has to change on your side. Nothing here asks you to replace a detector.

One honest difference between the offline pipeline and production. The batch feature build weights each identity by how often it appears in the whole dataset, which a live system cannot know. The streaming object uses the count it has seen so far. That costs 0.004 PR-AUC out of a contagion lift of 0.027 — measured, not assumed, in study_online_weights.py.

What we would fix first

Cap repeated blocks

A settled block currently marks every later payment by that customer, which let one account generate 1,172 false alarms. Capping repeats at three brings the per-transaction rate to 0.88% but drops recall from 19.4% to 10.6%. That is a business decision, not an engineering one, so it is exposed rather than chosen.

Rolling recalibration

The boundary is an empirical bound and it drifts. It should be refitted on a trailing window of confirmed outcomes on a schedule, with the achieved rate logged every time so drift is visible before it is expensive.

A fairness audit

Segment fairness is unmeasured. Contagion propagates along shared attributes, and shared attributes correlate with geography and device cost, so a disparate-impact review is required before this touches a real customer.
